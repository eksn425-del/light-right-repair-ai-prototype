日期：2026-05-25

一、这次为什么需要修正

你指出结果里出现了 100%、0% 这类绝对值，这个判断是对的。

目前 ABC 算法已经能跑通真实片区的工程流程，但算法 C 的安全验证和 final_report 的改造后指标仍然属于“框架版估计”，不是实测级、法规审查级或专业光环境软件级结论。因此：

1. safety_score = 100.0
   不能写成“方案绝对安全”。
   应改写为：“在当前简化安全规则和已提交道路/节点信息下，候选方案未触发规则违例，得到框架内最高评分。”

2. accessible_route_ratio = 1.0
   不能写成“100%无障碍覆盖”。
   应改写为：“在当前抽象路网和节点模型中，可达性规则未发现阻断；真实坡度、台阶、铺装、栏杆、临水边界仍需人工复核。”

3. algorithm_design 的 dark_zone_ratio = 0.0
   不能写成“暗区完全消除”。
   当前 final_report 中这是基于候选方案估计增益的汇总表达，并不是对干预后完整 OBJ 重新做一次真实光照模拟。
   应改写为：“算法方案预计可显著降低暗区比例；当前版本用于方案排序，不作为最终光环境定量结论。”

4. light_equity_improvement = 1.0
   不能写成“光权提升 100%”。
   应改写为：“在当前归一化评价口径中，算法方案相对基线取得最高等级的预期改善。”

二、GitHub / Skill 检索结果

我检索了与 Codex skills、科研、算法、可复现分析相关的公开资源，结论如下：

1. OpenAI 官方 skills 仓库
   地址：https://github.com/openai/skills
   作用：这是 Codex skills 的官方目录，说明 skills 是一套可复用的任务说明、脚本和资源封装方式。它适合把“重复性的研究流程”固化下来。

2. Awesome Scientific Skills
   地址：https://github.com/InternScience/Awesome-Scientific-Skills
   作用：偏科学研究场景，强调文献、数据分析、科研写作等 skill 集合。它对我们有启发，但不是建筑光照/空间决策的现成答案。

3. Deep Research Skills
   地址：https://github.com/Weizhena/Deep-Research-skills
   作用：偏深度研究流程组织，适合文献综述、资料整合、研究报告，不直接解决我们的空间算法验证问题。

4. 其他 research / reproducibility 类资源
   这些资源共同说明一件事：科研输出不能只给一个单点结论，必须同时给出方法、假设、数据边界、不确定性、复核步骤和可重复运行记录。

三、对本项目最适合的做法

不建议为了这个项目安装一堆泛用 research skill。
更适合的是给“光权修复”项目建立一套自己的科研化约束：

1. 所有算法结果必须区分三类数值：
   - measured：现场实测或人工确认数据；
   - simulated：模型模拟数据；
   - estimated：简化算法估计数据。

2. 所有百分比结果必须附带口径：
   例如：
   - “规则内通过率”
   - “抽象路网可达率”
   - “估计暗区比例”
   - “归一化改善指数”

3. 禁止在论文中直接使用绝对化表述：
   不写：
   - 完全消除暗区
   - 100%安全
   - 绝对最优
   - 精确证明

   改写为：
   - 显著降低暗区
   - 在当前规则框架内通过安全筛查
   - 在候选方案中综合评分最高
   - 为人工设计提供可量化辅助依据

4. 增加敏感性分析：
   当前已经有 8m 网格预测试和 6m 网格正式测试。
   建议论文中写：
   - 8m 网格：平均采光小时约 6.638h，暗区比例约 14.49%
   - 6m 网格：平均采光小时约 6.422h，暗区比例约 17.55%
   - 两种网格下最优候选均为 candidate_01，说明推荐方向具有一定稳定性。

5. 增加人工复核表：
   算法输出以后，建筑组需要人工检查：
   - 干预点是否真的位于可改造建筑；
   - 是否影响 C42 幼儿园；
   - 是否破坏主要道路、消防通行或邻里出入口；
   - 是否与现场照片、居民活动点、铺装高差矛盾；
   - 是否符合最终人工设计意图。

四、对 ABC 三步的修正建议

A 诊断层：
保持不变，但输出名称建议从“诊断结论”改为“简化光照诊断结果”。
热力图可以用于发现问题区域，但不能替代专业日照分析。

B 决策层：
保持“最小干预”逻辑不变。
候选方案仍然有效，但应解释为“候选干预建议”，不是自动生成的最终设计。

C 验证层：
需要把 100 分制解释清楚：
当前 C 是“规则筛查器”，不是“安全审图器”。
100 分表示未触发当前输入数据里的规则违例，不表示真实建成环境完全安全。

final_report：
建议把 algorithm_design 的若干指标改为：
“estimated / normalized / framework_score”，避免看起来像实测结论。

五、接下来我建议怎么改工程

建议在工程里增加一个 research_validation 层，专门处理论文口径：

1. 输出 uncertainty_notes.md
   说明模型简化、数据来源、误差风险。

2. 输出 sensitivity_summary.csv
   对比不同网格精度、不同权重下的结果稳定性。

3. 输出 paper_ready_metrics.csv
   只放适合论文展示的指标，并标注 measured / simulated / estimated。

4. 输出 manual_review_checklist.csv
   给建筑组逐项勾选，防止算法建议脱离真实场地。
