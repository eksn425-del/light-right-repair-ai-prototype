【给 Codex 的项目总览】

一、项目是什么
这是一个面向旧街区/城中村微更新的 AI + 建筑空间研究项目。项目不是为了做炫技式软件，也不是单纯做效果图，而是希望把旧街区里的实际空间问题转化为可分析、可比较、可验证的流程，并最终服务于设计决策。

二、项目场景
项目基于闽南街道与城中村更新语境，研究对象偏向高密、采光不足、街道压抑、居住体验较弱的真实城市空间。场地与任务书来源于既有教学与更新背景，因此具备较强落地性和调查可操作性。

三、项目目标
本项目的核心目标有四个：
1. 找出旧街区中最需要优先干预的空间问题点。
2. 用量化方式分析这些问题，而不是停留在经验判断。
3. 为后续微更新设计提供决策支持。
4. 形成一个既适合建筑学表达、又能体现计算思维的研究型项目。

四、项目不是为了什么
1. 不是为了堆砌复杂术语或追求纯技术炫技。
2. 不是为了做大而全的数字孪生平台。
3. 不是为了依赖昂贵硬件、重扫描或高门槛商业插件。
4. 不是为了重复既有项目的做法。

五、与既有项目的关系
用户已有一个偏“人在空间中如何更好行动/理解空间”的既有项目，因此这个新项目需要保持关联但不能重复。当前项目的区别在于：
1. 前一个项目更关注人在既有空间中怎么行动。
2. 当前项目更关注空间本体应该如何被诊断、比较和修复。
3. 关系上是延续，不是复刻。

六、当前项目的核心理念
1. 以真实空间问题为起点，而不是以工具为起点。
2. 以可解释的量化分析支持设计，而不是只给出主观结论。
3. 以低成本、可执行的小团队协作方式推进。
4. 以“先诊断、再决策、再验证”的结构替代直接跳入设计。
5. 以建筑空间理解和计算分析结合的方式形成项目特色。

七、当前较稳定的研究逻辑
项目目前已收敛到“三层结构”：
1. 诊断层：识别哪些位置存在最突出的空间问题。
2. 决策层：比较不同微更新方式对空间质量的影响。
3. 验证层：对结果做基本可行性与体验层复核。

这套逻辑的意义是：先让问题可计算，再让方案可比较，最后让结论可说明。

八、当前最重要的切入点
当前最适合启动的切入点是“算法A”，也就是基础诊断层。它的任务不是生成最终设计，而是先把复杂的现状空间转成可计算的分析对象。它不要求一开始完成高精度精模，但至少需要：
1. 建筑轮廓。
2. 基本高度或层数。
3. 街巷边界与方向。
4. 场地朝向。
5. 重点节点位置。
6. 主要界面或关键居住面信息。

九、项目执行方式
项目采用“主控分析 + 协作支持”的方式推进：
1. 主控者负责研究框架、算法分析、任务拆解、结果整合。
2. 协作者负责基础建模、资料整理、节点信息收集、图面支持。
3. 每个支持任务都需要形成明确交付物，便于主控者继续分析。

十、当前已形成的成果类型
1. 项目方向筛选与定位。
2. HTML 版本的项目说明与系统表达。
3. 算法框架相关文档。
4. 技术组项目计划与执行大纲。
5. 任务拆解与飞书导入用任务清单。
6. 甘特图类时间安排成果。
7. 面向组员的项目说明文档。

十一、当前最想达到的结果
这个项目最终希望呈现的不是“一个孤立的软件功能”，而是一套完整研究表达：
1. 真实问题识别。
2. 可计算的分析方法。
3. 有逻辑的方案比较。
4. 能解释的阶段性结论。
5. 建筑学与计算方法结合的研究价值。

十二、当前推进状态
项目已从前期的方向发散阶段，进入“框架相对稳定、可以任务化推进”的阶段。现在最重要的是把资料、白模、节点、分析流程和交付逻辑对齐，让后续 AI 协作和人工协作都能持续推进。

十三、Codex 接手时最该理解的事
1. 这个项目的重点是“空间问题如何被量化并支持微更新决策”。
2. 用户希望项目保留建筑空间优势，同时体现 AI/计算/3D 方向价值。
3. 项目执行条件偏低成本、低设备依赖、适合本科团队。
4. 任何后续建议都应优先服务于“可落地、可解释、可展示”。
