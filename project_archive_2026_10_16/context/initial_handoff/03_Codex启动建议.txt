【Codex 启动建议】

一、启动目标
Codex 接手后，目标不是重新发明项目方向，而是快速进入当前已收敛的研究框架，延续已有成果并提高推进效率。

二、先理解什么
Codex 首先要理解的不是某个单独文件，而是以下四件事：
1. 项目研究对象是旧街区/城中村中的真实空间问题。
2. 项目当前最稳定的结构是“诊断层 - 决策层 - 验证层”。
3. 当前最适合优先推进的是基础诊断，也就是算法A相关内容。
4. 用户希望项目同时具备建筑学问题意识与计算分析价值。

三、Codex 需要知道的用户偏好
1. 用户偏好低成本、可实现、适合本科团队的方案。
2. 用户不希望项目和既有项目在方法与成果上显得重复。
3. 用户希望强调研究问题、方法路径、结果逻辑，而不是只展示工具操作。
4. 用户接受用编程和脚本辅助分析，但不希望方案过度依赖高门槛商业生态。

四、当前项目最合适的工作方式
1. 先做结构梳理，再做细节补充。
2. 先围绕已有文档整合共识，再提出新增建议。
3. 先支撑主控分析，再扩展表现层或产品层。
4. 一切新增工作都应绑定明确交付物与用途。

五、Codex 接手后建议优先执行的顺序
1. 读取项目主框架与算法相关文件。
2. 明确项目当前的研究问题、阶段目标、交付物结构。
3. 核对任务清单与时间安排，确保执行线和研究线一致。
4. 根据白模、节点、场地信息组织算法A所需输入。
5. 在此基础上，再讨论后续比较、验证和展示的细化。

六、算法A接手时应默认的理解
1. 算法A是诊断层，不是项目全部。
2. 算法A不一定要求完整精模，但一定要求可计算的简化空间表示。
3. 当前最重要的是把问题识别清楚，而不是过早做复杂生成。
4. 白模、节点、朝向、建筑高度和关键界面是分析起点。

七、项目输出应朝什么方向收束
Codex 后续所有工作建议围绕以下结果组织：
1. 研究问题表达更清晰。
2. 方法结构更稳定。
3. 任务与交付链条更明确。
4. 可视化表达更有助于讲述整个项目。
5. 后续无论做 HTML、文本、任务表还是算法说明，都能互相对齐。

八、不要做什么
1. 不要把项目改造成完全不同的新项目。
2. 不要忽略建筑空间语境，只从纯计算角度理解。
3. 不要一开始就扩展成大而全的平台工程。
4. 不要把重心放到难以落地的设备、采集或超高成本流程上。
5. 不要泄露用户的凭据、平台配置、敏感授权信息。

九、如果要继续推进，最优先补齐什么
1. 简化白模与节点信息。
2. 节点清单和建筑信息表。
3. 算法A输入要求与输出格式。
4. 阶段性图表和结果表达模板。
5. 团队分工和交付格式统一。

十、一句话交接结论
这是一个已经完成方向收敛、正在进入稳定执行阶段的建筑空间研究型 AI 项目。Codex 的任务不是重新定义它，而是顺着现有逻辑，把“问题识别 - 方法分析 - 决策支持 - 结果表达”这条链条继续做稳。
